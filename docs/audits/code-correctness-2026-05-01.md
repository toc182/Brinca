# Code Correctness Audit

**Audited:** 2026-05-01
**Scope:** src/, app/, modules/
**Method:** static analysis + targeted code reading (4 parallel investigation agents across data layer, mutations/queries, stores/auth/init, and components/hooks/timers)

---

## 1. Summary

**7 BLOCKER, 11 CRITICAL, 8 MEDIUM, 1 LOW.** The single most dangerous finding: an entire class of repository writes (currency ledger, accolade unlocks, measurements, external activities, session deletes) bypass the sync queue entirely — see `src/features/session-logging/repositories/currency-ledger.repository.ts:13-17` and four others. These writes look successful locally but never reach Supabase, so a reinstall silently destroys earned currency, accolades, body measurements, external activity entries, and deleted sessions reappear. A second BLOCKER class jams the sync engine on any poison-pill entry. **Verdict: not shippable. The offline-first contract is broken in five repositories and the queue itself is fragile.**

## 3. Patterns observed

- **Five entire repositories silently bypass `appendToQueue`** (currency-ledger, accolade, measurements, external-activity, session-delete) — the offline-first contract is implemented per-call instead of enforced architecturally; whoever forgets the queue append breaks sync silently. A linter rule, a wrapper helper that always queues, or a base-repository abstraction would prevent recurrence.
- **Sync queue entries written outside SQLite transactions** in two reorder paths — the local-truth and queue-truth divergence on crash is a structural flaw of "transaction then queue append" rather than "transaction includes queue append."
- **Auth/init errors are silently routed to onboarding** — `data` is destructured without `error` in two `_layout.tsx` recovery paths and the auth listener has no try/catch, so a transient Supabase error becomes a user-visible "you're not onboarded" or "blank screen forever."
- **Cache invalidation is hand-rolled per-screen** rather than co-located with mutations; missing/wrong query keys (`activities('')`, no invalidation on bonus, drill complete, measurement edit) make screens display stale data after writes.
- **Sync engine module-level state (`isRunning`, `consecutiveFailures`) is never cleaned up between drains**, combined with `getNextPending` having no poison-pill skip — a single permanently-failing entry jams the entire queue forever.

---

## 4. Recommendation

**Fix this week:** all 7 BLOCKERs. Start with the five repositories that omit `appendToQueue` (#1-#5) — these can be added in a single PR and are mechanical changes. Then fix the queue's head-of-line blocking (#6) by adding a `retry_count >= MAX_RETRIES` skip in `getNextPending` and resetting `consecutiveFailures` on `startSyncEngine`. Then fix the IntervalTimer closure (#7) by moving `phase` to a ref. **By end of sprint:** the 11 CRITICALs, prioritizing the auth/init error-handling holes (#12, #13) and the empty-string invalidation key (#15) since they cause user-visible misbehavior without crashes. **Pattern fixes:** introduce a `withQueuedWrite` helper that wraps `db.runAsync + appendToQueue` in a single transaction — closes #1-#5, #8, #9, #10 in one structural change.
